# Decisions log

Decisions made during the spec review of 2026-11-10. Each one says what was decided and why.
To change one, add a new entry that replaces it. Don't edit the old entry.

| # | Decision | Why | Rejected alternatives |
| --- | --- | --- | --- |
| D-01 | `CLAUDE.md` lives at the repo root; design docs live in `docs/`. | Files inside `.git/` are never tracked or pushed, and Claude Code loads `CLAUDE.md` only from the root. | Leaving them in `.git/docs/`. |
| D-02 | The MVP is every item marked MVP in `design.md` section 4. `CLAUDE.md` is a summary of it. | Two scope lists drifted apart. One source of truth avoids building the wrong thing. | Smaller MVP from the old `CLAUDE.md` list. |
| D-03 | Item states: sent → accepted → ready → delivered, plus cancelled and voided. Sync status (Queued / Sending / Sent ✓) is separate. | "queued" mixed up network status with kitchen status. Splitting them keeps both simple. | `placed → queued → …`; an extra "preparing" step. |
| D-04 | Accept and Ready are **per item**. | Lets the kitchen accept some items and query others; voids then apply per item. Cost: more taps at peak. An "Accept all" button is suggested but not decided. | Accept the whole round. |
| D-05 | Kitchen undo within 10 s, saved as a new event. | Mistaken taps happen. A new event keeps the audit log honest instead of rewriting history. | Delaying alerts; no undo. |
| D-06 | Ready alerts go to the table's current waiter; sales stay with the waiter who placed the item. | After a shift hand-over, the first waiter may have left. Credit for the sale doesn't move. | Original waiter only; both. |
| D-07 | Cancel vs Accept: the first to reach the café's Durable Object wins. | A Durable Object handles one message at a time, so the order is clear and needs no locks. | Cancel always wins. |
| D-08 | Discounts and free items are P2. | Not needed for the core loop; there's no Discount entity yet. | MVP free items; MVP full discounts. |
| D-09 | One Directory Durable Object for the system-wide lookups. | Telegram, pairing and login requests don't know their café. A Durable Object is strongly consistent and uses tech we already have. | D1 (new component); KV (changes take ~60 s, so revoking isn't instant). |
| D-10 | PINs are checked only by the server. No offline sign-in. | A 4–6 digit PIN hash stored on a tablet is cracked in milliseconds if the tablet is stolen. Cost: new sign-ins and voids need internet. | Caching waiter PIN hashes on the device. |
| D-11 | 5 wrong PINs = 5-minute lockout + Telegram alert; manager PINs are 6 digits. | Stops guessing a manager PIN to approve voids. Known side effect: someone can lock a user out on purpose, but the alert makes it visible. | Lockout only. |
| D-12 | Dashboard login through Cloudflare Access. | We store no passwords. 2FA-grade login for free (≤50 users). Strong password hashing may not fit in the Workers Free CPU limit. | Building our own email + password + TOTP. |
| D-13 | Device tokens are random and server-checked (only the hash is stored). No JWT. | "Revoke at once" and "deactivate instantly" need a server check. A JWT stays valid until it expires. | Short JWT + denylist. |
| D-14 | Pairing and link codes are single-use, last 10 minutes, are bound to one user or device, and are rate-limited. | 6-digit codes can be guessed without limits, and an unbound code lets anyone link any account. | Longer codes only. |
| D-15 | Money is stored as integer santim. Total sales = non-voided items; service charge is a separate line. | Floats drift by a santim in sums. A separate line keeps total sales equal to what the kitchen received. | Decimal/REAL storage. |
| D-16 | `received_at` (server time) is authoritative; `created_at` (device time) is kept for information. | Tablet clocks can be wrong and would put orders in the wrong business day. | Device time. |
| D-17 | A queued order gets the current server price; sold-out items still reach the kitchen, flagged. | Device prices are never trusted. Silently dropping food the customer ordered is worse than asking. | Rejecting sold-out items. |
| D-18 | Offline, only opening a table and sending new rounds can be queued. | Each other offline action adds a sync conflict case (e.g. a table closed offline while the kitchen marks items ready). | Queue everything. |
| D-19 | Monthly R2 archives are never auto-deleted; nightly backups are kept 30 days; point-in-time recovery is used too. | The tax retention period is unknown and may be years. Keeping too much is reversible; deleting too early is not. | Keep everything in the Durable Object; wait for the tax advisor. |
| D-20 | Sign-out is blocked while rounds are unsent; the dashboard warns before revoking or wiping such a device. | Unsent rounds exist only on that tablet. | Nothing extra. |
| D-21 | Soft delete only. | Old reports must keep working. | Hard delete. |
| D-22 | Weeks run Mon–Sun; Pagume is its own month; times are stored in UTC and computed in Addis time; the daily auto report is sent at the end of the business day. | One clear rule each; sending at the end of the business day includes late orders. | Merging Pagume into Nehase; a fixed send time. |
| D-23 | Link codes are created for a named owner or manager; managers can't create codes for owners. | Stops a manager linking extra accounts to the owner's reports. | Owner-only. |
| D-24 | Tablet commands go over the WebSocket. | No new HTTPS handshake per command, and about 20× cheaper on the free plan (incoming WebSocket messages count 20:1). | REST for commands. |
| D-25 | The kitchen's audit "who" is the station device; there's no kitchen user role. | Fast with wet or gloved hands. | A kitchen PIN at shift start. |
| D-26 | The bar station is MVP. | Routing is cheap once `station_id` exists. | Kitchen only. |
| D-27 | Each café's Durable Object is created with a `locationHint`. | A Durable Object is placed near its first request and stays there. | Creating it from the café. |
| D-28 | Android Management API for kiosk mode and wipe. | Free; paid MDM conflicts with "no monthly cost". | Screen pinning; paid MDM. |
| D-29 | Personal phones are allowed (work profile recommended). | Cheaper for cafés. **Risk accepted:** no kiosk mode, no full wipe, and the app works off-site. Mitigation: revoke the token; work profile. | Café-owned devices only. |
| D-30 | Sentry free tier, with staff names and PINs scrubbed. | Crashes on café tablets are otherwise invisible. | Crashlytics; none. |
| D-31 | Usage alerts at 50% and 80% of free limits; Workers Paid ready to switch on. | Hitting a limit stops ordering until 03:00 Addis time. | Paid plan from day 1. |
| D-32 | Voids are allowed only from accepted or ready, never after delivered. | Keeps delivered sales final. **Risk accepted:** food sent back after delivery still counts in total sales, so reports can slightly overstate takings. | Void after delivery with manager PIN. |
| D-33 | A waiter can mark Delivered straight from accepted; the event records `skippedReady`. | The kitchen sometimes forgets to tap Ready; items must not get stuck on screens during a rush. | Requiring Ready first. |
| D-34 | Server tests use Vitest; TypeScript and Vitest are pinned to exact versions. | Cloudflare's Durable Object test tool is built on Vitest, so we won't switch runners later. Exact pins give the same results on every machine. | Node's built-in `node:test`. |
| D-35 | A repeated command returns `ALREADY_IN_STATE`, which the server treats as already done. | Double taps and resends after a reconnect are normal and must not show errors. | Rejecting duplicates as errors. |
| D-36 | Durable Object tests use `@cloudflare/vitest-plugin` and run inside Cloudflare's real runtime. | It's the maintained successor of `@cloudflare/vitest-pool-workers`, which is deprecated and only supported Vitest 4. Testing in the real runtime catches SQLite and transaction differences that fakes would miss. | The deprecated pool package with Vitest 4; fake storage in Node. |
| D-37 | Each command runs in one synchronous SQLite transaction (`transactionSync`, no `await` inside). | No other command can run in between (makes D-07 true), and a failed write rolls back the whole command. | Async storage calls with manual locking. |
| D-38 | `handleItemCommand` never throws: unexpected failures are logged and answered with `INTERNAL_ERROR`, which is not saved under the idempotency key. | A thrown error is reported by the runtime as uncaught, and the tablet still needs an answer. Since nothing was saved, retrying the same tap is safe. | Letting exceptions reach the caller. |
| D-39 | Refusals from the state machine are saved under the idempotency key; `ITEM_NOT_FOUND` is not. | A resent tap must get the same answer even if the item changed since. A missing item may simply not have arrived yet, so it is checked again on retry. | Saving every answer; saving only successes. |
| D-40 | Until device-token auth exists (slice 4), the public Worker answers 404 to everything. The café DO reads the connection's identity from internal `X-Cafe-*` headers. In slice 4 the Worker **must strip** any client-sent `X-Cafe-*` headers and set its own only after checking the token. | Lets the WebSocket transport be built and tested now without ever exposing an unauthenticated endpoint. | Building auth first; trusting identity sent in messages. |
| D-41 | The WebSocket protocol is JSON with a hand-written validator. The actor always comes from the connection, never from the message. Messages over 16 KB (counted in UTF-8 bytes) are refused. | JSON is small enough and easy to debug; no validation dependency needed for a handful of message types. Taking the actor from the message would let any tablet act as the kitchen. | Binary protocol; zod. |
| D-42 | Reconnect catch-up: `sync since:N` returns up to 500 missed events filtered to what that connection would have been pushed; more than that returns `reloadRequired`. | Push alone loses events on every Wi-Fi blip. A cap stops one stale tablet from making the DO send an unbounded reply. | No catch-up; unlimited catch-up. |
| D-43 | In slice 2, item events are pushed to the item's station tablets and the live view only; waiter alerts arrive in slice 3 with table sessions. Pushes happen only after the transaction commits; replays and refusals are never pushed. | Waiter routing needs the table's current waiter, which doesn't exist yet. A push before commit could show a state that is later rolled back. | Minimal sessions now. |
| D-44 | A table can be closed only when every item is delivered, cancelled or voided (`ITEMS_NOT_FINISHED`). | Stops a table showing as free while food is still coming, and keeps the kitchen screen consistent. | Closing anyway with a warning. |
| D-45 | A round the tablet marks `queuedOffline` is never refused for a table conflict: it joins the table's open session (or a new one), stays credited to the sender, and is flagged `table_taken`, `session_closed` or `not_your_table` to the kitchen, the table's waiter and the live view. **Accepted risk:** a buggy or tampered tablet could set the flag to bypass D-46; every such round is visibly flagged and logged. | Goal 3: zero lost orders. A live round's waiter is at the table and can fix an error immediately; a queued round's waiter may not notice for minutes. | Refusing and keeping the round on the tablet. |
| D-46 | Only the session's current waiter may send live rounds to it or close it (`NOT_YOUR_TABLE`); a manager override comes with roles in slice 4. | Keeps sales credit and alerts unambiguous ("own tables" in the permissions matrix). | Any staff member. |
| D-47 | Until the first deploy, the SQLite schema is edited in place. Before the first deploy it becomes numbered migrations. | Nothing is deployed, so there is no data to migrate yet; editing a `CREATE TABLE` after deploy would do nothing on existing cafés. | Migrations from day one. |
| D-48 | A new round's tickets are stored as `item.sent` events (ticket snapshot in `details`), not only pushed. | One mechanism (`seq` + `sync`) then covers tickets too: a kitchen tablet that missed a push still gets the ticket on reconnect. | Push-only tickets. |
| D-49 | Slice 3 is split: 3a sessions and rounds, 3b options/add-ons, sold-out toggle and live table states, 3c move/merge/hand-over. | Keeps each change small enough to review. | One big slice. |
| D-50 | Device tokens look like `<venueId>.<routeTag>.<secret>` and are checked in the café DO, not the Directory DO (**replaces the device-token part of D-09**). `routeTag` is an HMAC of the venue id, so the Worker refuses a forged venue before waking or creating any Durable Object. | One hop fewer on every connect (speed is #1), and revocation lives in one place. Without the tag, made-up venue ids would each create an empty Durable Object and use up free-plan requests and storage. | A Directory lookup on every connect. |
| D-51 | PINs are stored as HMAC-SHA256(key derived from the `SERVER_SECRET` Cloudflare secret, salt:PIN). Tokens are stored as plain SHA-256. One secret gives separate keys per purpose (`pin`, `route`). | A PIN has only 10⁴–10⁶ values, so any unkeyed hash is cracked in milliseconds from a leaked database; the key never touches the database. Under 1 ms of CPU, inside the free-plan limit. Tokens are 256-bit random, so SHA-256 is enough. | PBKDF2 (still crackable at this PIN size; CPU-heavy). |
| D-52 | Pairing-code guessing is limited to 5 failures per IP per hour plus 100 failures per hour globally (**replaces D-14's "code burned after 5 failed tries"**). | A wrong guess can't be tied to the code it was aimed at, so a per-code count is impossible. The global cap stops guessing spread over many IPs; with 10-minute codes the chance of hitting any live code is about 1 in 10,000 per hour. Side effect: an attacker can pause pairing for an hour, which is rare and harmless. | Per-code counters; longer codes. |
| D-53 | Waiters stay signed in until they sign out ("end of shift"); until business days exist, a session also ends after 16 hours. **Accepted risk:** on a shared tablet, the next person can act under the signed-in waiter's name until sign-out. | The user prefers no idle sign-out. The 16-hour cap stops a forgotten tablet staying signed in for days. | 30 minutes idle; 10 minutes idle. |
| D-54 | PIN sign-in is a REST call that returns a staff session token; the waiter tablet then opens its WebSocket with the device token and the session token. Every WebSocket message re-checks that the device and session are still valid. | WebSocket tags are fixed when a socket is accepted, so a user can't sign in inside an open socket. Re-checking per message makes revoke, deactivate, sign-out and expiry take effect on the next tap. | Signing in over the WebSocket. |
| D-55 | Async hashing happens first; the lockout check, PIN comparison and counter update then run in one synchronous step. | An `await` lets other messages run in between, so parallel guesses could otherwise slip past the lockout (tested). | Hashing inside the check. |
| D-56 | Slice 4 is split: 4a staff, PINs, sessions, devices, pairing, Worker routes, revoke and deactivate, waiter names on tickets; 4b manager-PIN voids (the server sets `approvedBy`). | Keeps each change reviewable. | One big slice. |
| D-57 | A void needs either a typed manager PIN (`managerId` + 6-digit `managerPin`), checked by the server, or a signed-in active manager/owner on the tablet. Only the server sets `approvedBy`; a tablet that sends it gets `INVALID_MESSAGE`. **Accepted risk:** with end-of-shift sessions (D-53), anyone who picks up a manager's unattended tablet can void until the manager signs out; every void records the approver and reason. | Closes the gap where a waiter could approve their own void (slice 2 risk). The user prefers no PIN re-entry for signed-in managers. | Always requiring a fresh PIN (step-up). |
| D-58 | Sign-in and void approval share one PIN check (`checkPin`) and one lockout per person: 5 wrong PINs anywhere lock for 5 minutes. A user with the wrong role gets `INVALID` without a failure being counted. | Stops guessing a manager PIN through the void screen to dodge the sign-in limit. Not counting wrong-role attempts stops people locking a waiter out by typing their id into the manager box. | Separate counters. |
| D-59 | The typed PIN is hashed before the transaction and never stored: it is left out of the idempotency fingerprint (only `managerId` is in it), and approval failures are not saved under the idempotency key. | The fingerprint is stored in `processed_commands`, so a PIN in it would sit in the database in plain text. Not saving failures lets the same tap be retried with the right PIN. | Hashing the PIN into the fingerprint. |
| D-60 | Each Durable Object runs numbered migrations on startup (`schema_migrations` table); migration 1 is the schema as of slice 4, frozen (**replaces D-47**). Migrations are append-only and additive only; each runs in its own transaction; a failure rolls back and throws; a database newer than the code logs a warning and keeps working. | Editing a `CREATE TABLE` does nothing on cafés that already exist. Additive-only keeps a rolled-back deploy working. A half-applied schema is worse than a loud failure. | Editing the schema in place; down-migrations. |
| D-61 | A daily Durable Object alarm deletes `processed_commands` older than 7 days (the idempotency window), ended or expired staff sessions older than 7 days, and, in the Directory, used or expired pairing codes and rate-limit windows older than an hour. Orders, items and events are never deleted by cleanup. | Stops bookkeeping tables growing forever inside the 1 GB per-café limit. A resend after a week is very unlikely, and even then the order id's primary key stops a duplicate. | No cleanup; a Cron Trigger that wakes every café. |
| D-62 | Every dashboard request's `Cf-Access-Jwt-Assertion` is verified in the Worker: RS256 only, signature against Access's public keys (cached 1 h, refetched at most once a minute for an unknown key id), issuer = team domain, audience = the app's AUD tag, expiry/not-before with 60 s skew, and an email claim. Test keys can be injected only when the team domain ends in `.invalid`. | Anyone can send that header straight to the Worker, so trusting it unverified would let anyone pick an identity. Refusing `none`/HS256 blocks algorithm-confusion attacks. The `.invalid` rule means the test private key (in the repo) can never be trusted in production. | Trusting the header; a JWT library (new dependency). |
| D-63 | State-changing admin requests must carry `Origin` equal to our own origin and `Content-Type: application/json`. | Browsers send the Access cookie on cross-site requests too (CSRF). A forged form can't send JSON without a CORS preflight, and same-origin hosting means no CORS is ever allowed. | CSRF tokens. |
| D-64 | Cafés are created by the installer with `npm run new-cafe` (POST /installer/venues, protected by the `INSTALLER_SECRET` secret); the secret comes from an environment variable and the owner PIN from a prompt. | Café owners never see installer powers; no extra privileged role in the dashboard. Keeping secrets out of command-line arguments keeps them out of shell history. | An installer area in the dashboard. |
| D-65 | The dashboard is served by the same Worker as the API (same origin, `/admin/`), replacing the separate `admin.` and `api.` hosts in design.md §6. | No CORS rules, simpler CSRF protection, one deploy. | A separate Pages site. |
| D-66 | Dashboard logins: managers and owners have an `email` (migration 2); the Directory maps each email to exactly one café and staff member (unique system-wide). The café re-checks role and active flag on every request, so deactivation removes dashboard access at once. Waiters can't use the dashboard even with an email. | Access proves who owns the email; the café stays the source of truth for permissions. | Permissions stored in the Directory. |
| D-67 | Menu and category names: English is required, Amharic optional; screens fall back to English when Amharic is empty. `menu_items.name` is the English name (columns are never renamed). **Replaces** "Amharic first-class" for menu names in design.md §11 (app text and fonts stay Amharic-ready). | The user prefers faster setup for English menus. | Amharic required; both required. |
| D-68 | Stations are fixed to `kitchen` and `bar` (K-10) for menu items and station tablets. | Matches the MVP; a simple choice in the dashboard. Configurable stations would be a later migration. | A configurable stations table now. |
| D-69 | Orders copy both names (`name` English + `name_am`) when sent; tickets carry both, so the kitchen tablet and reports can show either. | Mixed-language staff; a later menu rename never changes old tickets or reports (like prices, D-17). | One language on tickets. |
| D-70 | Prices are entered as ETB text with at most 2 decimals ("180", "42.50") and stored as santim; JSON numbers are refused. Tablets download the menu with both names (the `?lang=` parameter in design §8 is dropped). | A JSON number like 42.5 is a binary float; money must never pass through one. Both names let the app switch language offline. | Accepting numbers; per-language downloads. |
| D-71 | The Worker serves the dashboard's built files itself under `/admin/` (`run_worker_first`, `src/dashboard.ts`): app routes fall back to `index.html`, missing hashed assets stay 404. Every page gets a strict CSP (own scripts and styles only, no inline), `frame-ancestors 'none'`, `nosniff` and `Referrer-Policy: same-origin`; `index.html` is never cached, hashed assets for a year. The build goes to `server/public/admin` (gitignored; `public/` itself is committed) so server tests never depend on a dashboard build. | Cloudflare's own single-page-app fallback could answer a tablet's `GET /menu` with `index.html`. The CSP blocks injected scripts; no framing blocks clickjacking. | Cloudflare SPA mode; a separate Pages site (D-65). |
| D-72 | Dashboard: minimal libraries (React, React DOM, Vite and its React plugin; plain CSS; navigation by `#hash`), English only with every text in `admin/src/texts.ts`, component tests with Testing Library + jsdom. | Few pages and forms: libraries would add more to maintain than they save. One texts file makes Amharic a later addition, not a rewrite. | react-router, TanStack Query, Tailwind; manual testing only. |
| D-73 | Local dashboard development logs in through Vite's proxy, which adds an Access token signed with the TEST-ONLY key for a `.invalid` team (`server/scripts/dev-access-vars.mjs` writes the matching `.dev.vars`). The proxy adds only that token; Host and the browser's Origin pass through unchanged. | No Cloudflare Access on a laptop. Production can never accept the test key (D-62). An earlier version also rewrote Origin, which broke every change with `CSRF` (found by the end-to-end run): Origin and Host must agree, as they do in production. | A dev-only login bypass in the server. |
| D-74 | Table states on the floor map: free, seated (no items yet), ordered (something waits for the kitchen), accepted, ready, delivered. Always derived from the open session's items; priority ready > ordered > accepted > delivered. After every command the touched tables are recomputed inside its transaction and pushed to all waiters (`waiters` tag) and the live view **only if the state changed** (remembered in `table_live_state`). | "Ready" must win so a pick-up is never hidden behind a new round. Pushing only changes keeps messages few (free plan). | Free/open only; pushing every recomputation. |
| D-75 | Sold-out: the station tablet changes only its own items (`menu.sold_out` over the WebSocket, audited); managers can change it in the dashboard; both push to all waiters, the item's station and the live view. Reset is manual: "back in stock" is also the undo. | K-05/W-10; automatic reset needs business-day settings that don't exist yet. | Kitchen only; automatic morning reset. |
| D-76 | `npm test` in `server/` fails if fewer test files ran than exist in `test/` (`scripts/test.mjs`). | Three runs silently reported fewer tests and still exited green; once a planted bug went unnoticed that way. The cause is not found yet, so a missing file must make the run red. | Trusting Vitest's exit code alone. |
